CREATE do hĺbky — a ako zhodnotiť návrh od AI

Minule nám CREATE napísala AI z nášho ERD diagramu a my sme ho len spustili. Dnes sa staneme recenzentmi: naučíme sa, čo všetko sa v tabuľke nastavuje, a potom posúdime, či je AI návrh naozaj dobrý.

Štyri „nastavenia" každého stĺpca:
→ dátový typ
→ smie byť NULL?
→ kľúče (PK/FK)
→ doména (CHECK). Týmto poradím prejdeme každý stĺpec.

Nastavenia 1

Dátový typ — čo do ktorého stĺpca

TypNa čoU nás
INTcelé číslaid, zakaznik_id, mnozstvo
VARCHAR(n)text do dĺžky nmeno, email, nazov, stav
DATEdátumdatum
DECIMAL(8,2)peniaze (2 desatinné)cena
Peniaze nikdy ako FLOAT — vznikajú zaokrúhľovacie chyby (napr. 0,1 + 0,2 ≠ 0,3). Vždy DECIMAL.
Otázka: prečo je datum ako VARCHAR(20) zlý nápad? (Nápoveda: ako zoradíš „10.1.2026" a „9.2.2026" ako text?)

Nastavenia 2

NOT NULL — smie byť stĺpec prázdny?

NOT NULL znamená „táto hodnota musí byť vyplnená". Pýtame sa pri každom stĺpci: dáva zmysel záznam bez nej?

StĺpecNOT NULL?Prečo
zakaznik.menoánozákazník bez mena nedáva zmysel
zakaznik.emailniee-mail nemusíme mať ku každému
faktura.zakaznik_idánofaktúra musí patriť zákazníkovi
faktura_polozka.mnozstvoánopoložka bez množstva nemá zmysel

Nastavenie 3

Kľúče — a kedy AUTO_INCREMENT

PRIMARY KEY = jednoznačná identifikácia riadku. FOREIGN KEY = odkaz na riadok v inej tabuľke (tvrdá referenčná integrita — už sme videli, že databáza nepustí položku na neexistujúcu faktúru).

Kto určuje id: databáza, alebo my?

StĺpecAkoPrečo
zakaznik.id, polozka_cennika.idAUTO_INCREMENTumelé poradové id — nech ho čísluje databáza
faktura.idbez AUTO_INCREMENTčíslo faktúry je naše (2026001, 2026002…) — zadávame ho sami
AUTO_INCREMENT je skvelé pre „technické" id, ktoré nikoho nezaujíma. Ak má číslo význam v reálnom svete (číslo faktúry, evidenčné číslo), zadávame si ho sami.

Nastavenie 4 — nové

CHECK — povolené hodnoty (doména)

CHECK stráži, aké hodnoty do stĺpca vôbec smú. Je to presne tá doména, ktorú sme v Exceli strážili cez Overenie údajov — tu je zabudovaná priamo v tabuľke.

CREATE TABLE faktura_polozka (
    ...
    mnozstvo  INT NOT NULL CHECK (mnozstvo > 0)
);

CREATE TABLE polozka_cennika (
    ...
    cena  DECIMAL(8,2) NOT NULL CHECK (cena >= 0)
);
Spomeň si na faktúrový mini-projekt: záporné množstvo −2, cena −120, množstvo 0. Takéto hodnoty CHECK rovno odmietne — nemusíme ich „zakrúžkovať" dodatočne.
Náš server: MariaDB 10.4 — CHECK vynucuje (platí od MariaDB 10.2+ / MySQL 8.0.16+; staršie MySQL ho len ticho ignoruje). Takže o chvíľu uvidíme, ako naozaj odmietne zlú hodnotu.

Metóda

Ako recenzovať návrh od AI

AI návrh sa väčšinou spustí bez chyby — to ešte neznamená, že je správny. Prejdi každý stĺpec štyrmi nastaveniami:

#Otázka
1Má stĺpec správny dátový typ? (peniaze = DECIMAL, dátum = DATE)
2Smie byť prázdny, alebo tam patrí NOT NULL?
3Sú kľúče v poriadku? PK správny, chýba niekde FOREIGN KEY? AUTO_INCREMENT tam, kde má byť?
4Nemá mať stĺpec CHECK (povolené hodnoty)?

Naživo — po spustení opravenej verzie

Databáza odmietne zlú hodnotu

Opravený návrh má CHECK aj FOREIGN KEY. Skúsime schválne tri chyby — každú databáza odmietne (v Exceli by prešli):

-- CHECK: záporná cena
INSERT INTO polozka_cennika (nazov, cena) VALUES ('test', -5);
-- → Check constraint 'cena' failed

-- CHECK: nulové množstvo
INSERT INTO faktura_polozka (faktura_id, polozka_cennika_id, mnozstvo)
VALUES (2026001, 1, 0);
-- → Check constraint failed

-- FOREIGN KEY: položka na neexistujúcu faktúru 9999
INSERT INTO faktura_polozka (faktura_id, polozka_cennika_id, mnozstvo)
VALUES (9999, 1, 1);
-- → Cannot add or update a child row: a foreign key constraint fails
Presne toto bol v Exceli len „mäkký" zoznam v Overení údajov — dal sa obísť. Databáza to stráži tvrdo.
